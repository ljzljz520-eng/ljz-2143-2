# 校园活动签到系统

一个无第三方运行依赖的校园活动签到示例，包含：

- **C 大屏**：展示当前活动/场次、主视觉、屏幕旋转角、**确认人数与暂定/待裁决人数**；不返回或展示姓名、学号、事件明细等个人敏感信息。
- **签到终端**：在线扫码走服务端强一致事务；离线时仅按票据范围本地暂存，恢复网络后批量合并和重试。
- **Web 工作台**：管理场次、参与资格、人工补签、撤销、离线/迟到冲突处置、设备同步进度、人数重算和大屏发布。
- **服务端**：持久化活动、场次、人员资格、不可变签到事件、暂存冲突、设备批次同步进度和当前发布版本。

## 一致性策略：在线强一致，离线只产生暂定人数

本项目没有采用“终端离线各自计数、之后简单相加”的方案，因为它会遇到：

1. 两台设备同时扫同一人导致重复计数；
2. 撤销已经发生，但旧设备的迟到扫描又把人数加回；
3. 请求可能已在服务器成功，响应丢失后终端重试；
4. 活动换场后，旧队列被错误合并进新场次；
5. 图片、网络等展示层故障被误认为签到业务故障。

因此选择：

- **在线**：每个扫码请求在服务端串行事务内完成资格校验、票据范围校验、幂等检查、事件追加、计数重放、原子落盘和版本递增。终端立即得到确认结果。
- **离线**：票据 HMAC 绑定 `activityId + sessionId + personId + 过期时间`。终端只把请求放入本地队列并显示暂定人数；大屏确认人数不包含未成功提交的队列。
- **合并**：恢复网络后终端按当前场次提交批次，服务端复用同一套领域规则。重复请求被幂等拒绝；票据属于旧场次时整批中止；需要人工判断的请求进入工作台冲突队列。
- **重算**：确认人数永远由不可变事件按 `seq` 重放得到，不维护可被覆盖的 `checkedIn: true/false` 字段。

## 不可变事件模型

每个场次中，一个人最多有一个“当前有效签到”，但历史事件不覆盖、不删除：

| 事件 | 含义 |
| --- | --- |
| `CHECK_IN` | 首次扫码入场 |
| `REVOKE` | 工作台撤销当前有效签到 |
| `RE_ENTRY` | 撤销之后再次扫码入场 |
| `MANUAL_CHECKIN` | 工作台接受冲突或人工补签 |
| `SCAN_REJECTED` | 重复扫码、撤销后迟到等拒绝记录，仅用于审计 |

重放规则：按事件 `seq` 排序，遇到有效入场事件设置当前签到，遇到 `REVOKE` 删除当前签到。同场重复扫码只会新增 `SCAN_REJECTED`，不会产生第二个有效签到；撤销后再次入场会保留完整的 `CHECK_IN -> REVOKE -> RE_ENTRY` 历史。

## 离线票据和换场隔离

票据由工作台签发，载荷包含：

- `aid`：活动 ID
- `sid`：场次 ID
- `pid`：人员 ID
- `tid`：票据 ID
- `iat` / `exp`：签发和过期时间
- HMAC-SHA256 签名

离线队列中的每条请求也带活动、场次、幂等键和原始扫描时间。终端合并时只提交当前选择场次的队列；服务端再次校验票据签名、有效期和场次。旧场次票据提交到新场次会返回 `ticket_wrong_session`，旧队列继续保留在终端，不会进入新场次暂定或确认人数。

## 冲突处置

工作台提供三种处置：

- **接受**：管理员确认请求有效，必要时补授资格，并追加新的独立入场/补签事件。
- **替换**：先追加 `REVOKE`，再追加 `MANUAL_CHECKIN`，适用于需要替换旧有效签到的场景。
- **丢弃**：关闭暂存项，不改变确认人数。

典型场景：扫码发生在撤销之前，但事件在撤销之后才到达服务器。系统不会让迟到事件复活已撤销签到，而是把请求放入冲突队列；原始拒绝事件和处置事件均可审计。

## 原子发布和大屏容错

发布接口在同一个服务端事务中替换完整 `publication`：

- 活动 ID / 名称
- 当前场次 ID / 名称
- 主视觉 URL
- 标题、副标题、主题
- 旋转角 `0/90/180/270`
- 当场次重放计数

因此客户端只能看到完整的新版本，不会出现“新人数字 + 旧场次名”的撕裂状态。SSE 推送失败时大屏使用 5 秒轮询兜底；图片预加载失败时移除损坏背景并保留纯 CSS 主屏、当前场次和人数，签到接口不受影响。

## HTTP API 摘要

### 大屏与工作台

- `GET /api/screen`：只含公开展示状态和聚合计数，无个人明细。
- `GET /api/admin`：活动、场次、资格、事件、冲突、设备同步和发布状态。
- `GET /api/events?scope=public|admin`：SSE，初始发送 `hello`，提交后发送 `commit`。

### 终端

- `POST /api/checkins`：在线扫码、人工补签或撤销。
- `POST /api/sync`：离线批次合并。
- `POST /api/tickets`：工作台为有权限的人签发离线票据。

### 管理

- `POST /api/admin/sessions`：创建场次和初始资格。
- `POST /api/admin/eligibility`：补授资格。
- `POST /api/admin/publish`：原子发布大屏版本。
- `POST /api/admin/recompute`：从事件重放所有人数。
- `POST /api/admin/staging/:id/resolve`：接受、替换或丢弃冲突。

## 验收覆盖

`test/acceptance.test.js` 覆盖 9 个关键验收点：

1. 两台设备同时扫同一人，只形成一个有效签到；
2. 撤销后同一旧请求迟到，幂等返回且不能复活签到；
3. 撤销后另一个迟到旧扫描进入冲突、暂定和确认分离；
4. 服务器可能成功而终端重试，同一幂等键不重复计数；
5. 撤销后再次入场保留三个独立事件；
6. 一个人参加多个场次，场次计数独立；
7. 票据绑定活动/场次/有效期，旧队列不能进入新场次；
8. 工作台接受/替换/丢弃冲突并提供重算结果；
9. 发布时当前场次、人数、主视觉和旋转角处于同一个版本，大屏数据无个人敏感信息。

## 数据持久化

默认数据文件为 `data/checkin.json`。写入采用“临时文件 + rename”原子替换，进程内所有变更经同一个串行 `mutate()` 边界提交。该实现适合演示和轻量部署；生产环境可把 `Store` 替换为带事务的 SQLite/PostgreSQL 适配器，而无需修改事件重放和冲突裁决领域逻辑。
